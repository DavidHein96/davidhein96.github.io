## The Problem with Vibe Coding

AI coding tools are genuinely good at generating features fast. The problem is they have no opinion about whether the feature they just wrote introduced a SQL injection, broke your TypeScript types, shipped a 2GB container image, or quietly removed the security header you spent an afternoon configuring. The model's job is to make the code work. Keeping the code safe, correct, and maintainable is still your job.

The answer isn't to avoid AI-assisted coding. It's to build a harness that catches what the model misses — automatically, on every change, before anything hits production.

This post is a tour of [**fullstackvibe**](https://github.com/DavidHein96/fullstackvibe), a full stack reference template I maintain as a starting point for new projects. The stack is FastAPI + React + PostgreSQL, packaged as containers. But the interesting part isn't the stack choices — it's the CI/CD harness that enforces correctness and security regardless of how the code was written.

## The Makefile Is the Source of Truth

The most important architectural decision in this template isn't a framework choice — it's that the Makefile and the GitHub Actions workflows run the same commands. When `make ci-fast` passes locally, CI passes. No surprises.

```makefile
ci-fast: fix typecheck generate-openapi   ## Run fast CI checks (no tests)

ci-test: test                             ## Run all tests

ci-security: security security-container-all  ## Run security scans
```

Each of those targets composes smaller ones:

```makefile
fix: fix-python fix-frontend

fix-python:
    uv run ruff format apps/backend/src
    uv run ruff check --fix apps/backend/src

fix-frontend:
    pnpm prettier --write .
    pnpm eslint --fix .

typecheck: typecheck-python typecheck-frontend

typecheck-python:
    uv run ty check apps/backend/src

typecheck-frontend:
    pnpm tsc --noEmit
```

The pattern: before you open a PR, you run `make ci-fast`. If it passes, CI passes. If the model generated something that fails a type check or lint rule, you find out immediately at your terminal rather than in a CI failure fifteen minutes later. When I'm using an AI tool to generate a chunk of code, `make fix && make typecheck` is the first thing I run — it's the fastest filter for catching obvious issues.

## Security Scanning: The Part Everyone Skips

Most "production-ready" templates treat security as an afterthought. This one runs four independent security checks on every PR and on a weekly schedule regardless of changes.

### SAST with Semgrep

Semgrep scans for known vulnerability patterns across the whole codebase — Python, JavaScript, React, Docker, GitHub Actions. It runs with both the standard policy packs and custom rules written for this specific stack:

```yaml
# semgrep.yml — custom rules
rules:
  - id: frontend-no-raw-innerhtml
    severity: HIGH
    message: "Use safeSetHTML() instead of direct innerHTML assignment"
    patterns:
      - pattern: $EL.innerHTML = $X
      - pattern: document.write($X)

  - id: frontend-no-insecure-tls-toggle
    severity: MEDIUM
    message: "TLS verification must not be disabled"
    patterns:
      - pattern: process.env.NODE_TLS_REJECT_UNAUTHORIZED = '0'
      - pattern: |
          {rejectUnauthorized: false}
```

The `frontend-no-raw-innerhtml` rule exists because React's `dangerouslySetInnerHTML` is already linted, but direct DOM manipulation in utility functions is easy to miss. `frontend-no-insecure-tls-toggle` catches a surprisingly common shortcut in development code that occasionally slips into production.

### Dependency Auditing

Both package ecosystems get scanned separately:

```makefile
security-deps:
    uv run pip-audit                  # Python dependencies
    pnpm audit --audit-level moderate  # Node dependencies
```

This runs on every PR and on a cron schedule every Sunday. Dependency vulnerabilities show up between PRs — a Sunday scan catches CVEs that landed during the week against your pinned versions.

### Container Scanning with Trivy

Three levels of Trivy scanning, each catching different things:

```makefile
security-container-backend:
    trivy image --severity CRITICAL,HIGH ghcr.io/$(REPO)/backend:latest

security: security-sast security-deps

ci-security: security security-container-all
```

- **Filesystem scan**: checks for vulnerabilities in the source code and lockfiles
- **Config scan**: checks Dockerfiles, docker-compose, and GitHub Actions for misconfigurations (CRITICAL, HIGH, and MEDIUM)
- **Container image scan**: scans the built image for OS-level vulnerabilities

Container scans only run on the main, dev, and nightly branches — they require a built image, so they're gated on the Docker build workflow completing.

### ESLint Secrets Detection

The frontend ESLint config includes `eslint-plugin-no-secrets` with a tolerance threshold, which flags strings that look like API keys, tokens, or credentials accidentally committed to frontend code. It's not a substitute for a proper secrets scanner, but it's caught things.

## Two Dockerfiles

Development and production have meaningfully different requirements, and trying to serve both with one Dockerfile produces something that's bad for both. This template maintains two:

**`Dockerfile.dev`** (Debian-based): - Hot reload via `uvicorn --reload` with the source code mounted as a volume — the container doesn't need to be rebuilt on every code change - Runs as root (dev convenience)

**`Dockerfile`** (Alpine multi-stage, production): - Stage 1 builds the virtualenv with `uv`, installs only non-dev dependencies - Stage 2 copies only the venv — no build tools, no source code - Validates OpenSSL version >= 3.0.0 at container startup - Non-root user (uid 1000) - Healthcheck hits `/health`

The Alpine base keeps the image small. The non-root user and the OpenSSL version check at startup are basic hardening that many templates skip — the runtime assertion catches cases where a base image update quietly downgrades a security dependency.

For local development, a `docker-compose.yml` wires together the dev backend, a local PostgreSQL container, and the Vite dev frontend with a proxy to the backend API.

## Testing with Testcontainers

The application uses PostgreSQL. Most tutorials solve the test database problem by switching to SQLite — which is fine until you hit a query that uses a Postgres-specific feature and your tests pass but production breaks.

This template uses [testcontainers](https://testcontainers-python.readthedocs.io/) to spin up a real PostgreSQL container for every test run:

```python
# The test setup spins up a real PostgreSQL container
# Alembic migrations run against it before tests start
# Torn down after the session
```

In GitHub Actions, a PostgreSQL service container runs alongside the test job, with health checks to wait for the database to be ready before tests start:

```yaml
services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_USER: test
      POSTGRES_PASSWORD: ${{ secrets.POSTGRES_PASSWORD }}
      POSTGRES_DB: testdb
    ports:
      - 5432:5432
    options: >-
      --health-cmd "pg_isready -U test"
      --health-interval 10s
      --health-timeout 5s
      --health-retries 5
```

Tests are marked with `unit`, `integration`, or `e2e` markers. Unit tests don't touch the database. Integration tests use the container. The separation matters when you want to run only fast tests in a tight feedback loop.

## The Type Generation Pipeline

One of the more useful features for a project with a separate frontend and backend: the OpenAPI schema generated by FastAPI becomes the TypeScript type definitions used by the frontend. `make check-types-sync` validates that they're in sync and fails CI if they're not.

```makefile
generate-openapi:
    uv run python -c "import json; from backend.main import app; \
        print(json.dumps(app.openapi()))" > packages/api-types/openapi.json

generate-types:
    pnpm openapi-typescript packages/api-types/openapi.json \
        -o packages/api-types/src/generated.ts

check-types-sync: generate-openapi generate-types
    git diff --exit-code packages/api-types/
```

If a backend route changes its response schema and the developer doesn't regenerate types, `check-types-sync` fails in CI. The frontend TypeScript compiler then catches any call sites that are now passing wrong types. This catches a category of integration bug — backend and frontend disagreeing on the shape of data — that usually only shows up in manual testing or production.

## GitHub Actions: Three Workflows

### `ci.yml` — Continuous Integration

Path-based change detection (via `dorny/paths-filter`) means frontend checks only run when frontend files changed, backend checks only run when backend files changed. On a monorepo with separate apps, running everything on every commit is wasteful and slow.

Concurrency cancels in-progress runs on the same branch — opening a PR, pushing a fixup commit, and pushing another fixup doesn't leave three CI runs running simultaneously.

A `ci-success` job aggregates the results of all conditional jobs into a single status that branch protection can require, solving the problem where conditional jobs show as "skipped" rather than "passed."

### `security.yml` — Security Scanning

Runs on push/PR, but also on a cron schedule every Sunday regardless of changes. The schedule matters because new CVEs land against your pinned dependencies without you changing anything.

### `build_docker.yml` — Docker Build and Push

Change detection determines which apps to build, then a matrix job builds and pushes to GitHub Container Registry. Tagged with both the git SHA and an environment name, so you can trace any deployed image back to the exact commit.

## What I Still Skip

**Auth is intentionally absent.** Auth is the most context-dependent layer in any web app — whether you reach for Clerk, Auth0, Supabase Auth, or roll your own JWT depends on your team size, compliance requirements, and how much you want to own. Baking a specific auth choice into a template locks in an opinion that's likely wrong for half the people using it. The FastAPI dependency injection structure is there to plug auth in, but the template doesn't prescribe what goes there.

**Pre-commit hooks.** The Makefile covers everything, but hooks would catch issues before a commit rather than before a push. I've found that the CI feedback loop is fast enough that hooks feel like friction during active development, but for a team setting they'd be worth adding.

**Observability.** The template has `structlog` wired up for structured logging, but there's no Sentry integration, no distributed tracing, no dashboards. That's mostly a matter of it being a template rather than a running production system — the hooks are there, but the specific monitoring stack depends too much on where you're deploying.

**E2E tests.** The `e2e` pytest marker is defined, but there are no E2E tests yet. Integration tests cover the API surface, but full browser-level testing would require Playwright or similar, and that's a bigger lift to set up correctly.
